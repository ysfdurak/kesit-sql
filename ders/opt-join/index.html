JOIN, EXISTS, IN ve alt sorgu maliyeti: erken süzme, gereksiz DISTINCT, SELECT *

Aynı sonucu veren yazımların planı, ilişkili alt sorgu, WHERE ve HAVING, DISTINCT ile örtülen çoğalma, SELECT * bedeli.

Uygulamada aç, 8 alıştırmayı çözÜcretsiz, hesap gerekmez, kurulum yok.

Bu sayfa dersin okuma sürümüdür. Metin bir kutuyu çalıştırmanı ya da adıma geçmeni söylüyorsa dersi uygulamada aç.

Senaryo: "Hesabı olan müşteriler"

Bu soruyu üç biçimde yazabilirsin. Hangisi hızlı? İnternette kesin cevaplar göreceksin. Doğrusu: motora ve veriye bağlı, ölç.

-- 1) EXISTS
SELECT c.customer_id FROM bank_customers c
WHERE EXISTS (SELECT 1 FROM bank_accounts a WHERE a.customer_id = c.customer_id);
-- 2) IN
SELECT c.customer_id FROM bank_customers c
WHERE c.customer_id IN (SELECT a.customer_id FROM bank_accounts a);
-- 3) JOIN + DISTINCT
SELECT DISTINCT c.customer_id FROM bank_customers c
JOIN bank_accounts a ON a.customer_id = c.customer_id;

SQLite ne yapıyor?

Aynı üç sorgunun planlarına bak ve süreleri karşılaştır. Burada indeks yokken EXISTS her müşteri için hesap tablosunu ilk eşleşmeye kadar tarar. "EXISTS her zaman hızlıdır" kuralının bu motorda geçerli olmadığını kendin görürsün.

EXPLAIN QUERY PLAN SELECT c.customer_id FROM bank_customers c
WHERE EXISTS (SELECT 1 FROM bank_accounts a WHERE a.customer_id = c.customer_id);
EXPLAIN QUERY PLAN SELECT c.customer_id FROM bank_customers c
WHERE c.customer_id IN (SELECT a.customer_id FROM bank_accounts a);

Çıkarım: kuralı ezberleme. bank_accounts (customer_id) indeksi eklenince SQLite'ta EXISTS de arama yapar. Yöntemi anlama göre seç: varlık soruyorsan EXISTS ya da IN, satırı çoğaltmak gerekmiyorsa JOIN + DISTINCT yazma.

NOT IN başka bir konuNOT IN ile NOT EXISTS farkı hız değil anlamdır. Alt sorguda tek bir NULL varsa NOT IN hiç satır döndürmez. Bu yüzden NOT EXISTS tercih edilir.

İlişkili alt sorgu (correlated subquery)

SELECT listesindeki ilişkili alt sorgu dış sorgunun her satırı için çalışır. İç tarafta indeks yoksa satır × satır iş çıkar.

EXPLAIN QUERY PLAN
SELECT c.customer_id, c.city,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS siparis
FROM customers c;

Plandaki CORRELATED SCALAR SUBQUERY ve altındaki SCAN a satırları bunu söylüyor. Önce toplayıp sonra birleştirince alt sorgu bir kez çalışır:

SELECT c.customer_id, c.city, COALESCE(o.siparis, 0) AS siparis
FROM customers c
LEFT JOIN (SELECT customer_id, COUNT(*) AS siparis FROM orders GROUP BY customer_id) o
  ON o.customer_id = c.customer_id;

LEFT JOIN ve COALESCE önemli: siparişi olmayan müşteride alt sorgu 0 veriyordu, düz JOIN o satırı kaybederdi.

Erken süzme

Mantıksal sırada HAVING gruplamadan sonra çalışır. Grup sütunu üzerindeki koşul için öğüt nettir: WHERE'de yaz. Ama hız farkı beklemeden önce planlara bak:

CREATE INDEX ix_tip ON bank_txns (txn_type);
EXPLAIN QUERY PLAN SELECT txn_type, COUNT(*) FROM bank_txns GROUP BY txn_type HAVING txn_type = 'faiz';
EXPLAIN QUERY PLAN SELECT txn_type, COUNT(*) FROM bank_txns WHERE txn_type = 'faiz' GROUP BY txn_type;

İki kutu da aynı planı veriyor: bu basit durumda motor koşulu kendisi öne alıyor. PostgreSQL de aynı şeyi yapıyor:

CREATE INDEX ix_tip ON bank_txns (txn_type);
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY OFF)
SELECT txn_type, COUNT(*) FROM bank_txns GROUP BY txn_type HAVING txn_type = 'faiz';

Yine de WHERE yaz. Niyetin açık kalır, ayrıca motorun koşulu öne alamadığı durumlar vardır. Birleştirmeli sorgularda da sor: "Bu büyük tablo birleşmeden önce daralabilir mi?" İyileştiriciler WHERE koşulunu çoğunlukla kendileri aşağı iter, ama LEFT JOIN, pencere fonksiyonu ve DISTINCT içeren alt sorgular bunu engelleyebilir. Emin olmanın yolu plandır.

CTE her zaman bedava değildir

CREATE INDEX ix_txn_time ON bank_txns (txn_time);
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY OFF)
WITH t AS (SELECT txn_id, txn_time FROM bank_txns) SELECT COUNT(*) FROM t WHERE txn_time >= '2024-11-01' AND txn_time < '2024-11-02';

Gereksiz DISTINCT ve SELECT *

  • DISTINCT çoğalmayı gizler. Birleştirme satırları çoğaltıyorsa önce nedenini düzelt. Sonuç doğru görünse bile iş iki kat yapılmıştır.
  • SELECT * kapsayan indeksi işe yaramaz hâle getirir ve sıralama belleğini büyütür. Aşağıdaki iki planda satır sayısı aynı, sıralama belleği farklı.
  • Sütun tabanlı ambarda fatura farkı: BigQuery'de okunan sütun kadar ödersin. Belgeye göre SELECT * sorgusuna LIMIT eklemek okunan veri miktarını değiştirmez.
